### 什么是Image, Container, Hub?

1. 镜像 (Image) —— “时空刻录的光盘 / 静态蓝图”
存在意义：镜像是一个只读的（Read-Only）静态模板。它里面包含了你的应用程序运行所需的一切“血缘基因”（比如：Ubuntu 操作系统精简版 + Python 3.10 + 你的 PySpark 代码）。

架构师视点：它就像是面向对象编程里的 Class（类），或者是冰冻封存的冷冻胚胎。它躺在硬盘里，不占用 CPU 和内存，它是绝对静态的、不可篡改的。

2. 容器 (Container) —— “运行中的实体 / 活性肉身”
存在意义：容器是镜像运行时的实体（Instance）。当你用 Docker 引擎去 run 一个镜像时，系统就会在内存中为它划出一块绝对隔离的独立时空，让它活过来。

架构师视点：它就像是面向对象编程里用 new 实例化出来的 Object（对象）。容器可以被启动、停止、删除。你在容器里无论怎么卸载、怎么搞破坏，只要容器一删，底层的镜像完好无损，绝不污染你原本的电脑系统！

3. 仓库 (Registry / Hub) —— “全球物流中转站 / 基因库”
存在意义：仓库是用来集中存放、托管镜像的云端中枢。最著名的就是官方的 Docker Hub。

架构师视点：它就像是大数据的 GitHub 或者是 Maven/Pip 源。全天下的架构师把自己手焊好的优质镜像 push 到仓库，你要用的时候直接一记 pull 网线拉满下载下来。

#### 生产背景

你需要写一个 Python 实时脚本，每秒钟监控一次核心订单目录。为了保证这个脚本在本地 Mac、DTU/Chalmers 实验室服务器、以及 AWS 云端生产集群上跑出来的**Python版本和库一模一样**，我们决定使用 Docker 进行交付。


---

#### 第一步：手焊本地代码与只读蓝图 —— 镜像 (Image) 的诞生

1. **写出生产代码**：你在本地 Mac 上创建了一个 `app.py` 脚本：
```python
# app.py
import time
print("🛰️ [Yuto Stream Monitor] 订单高频雷达开始通电监听...")
while True:
    print("⚙️ 正在扫描 Volumes 目录，当前未发现欺诈大单，状态：安全。")
    time.sleep(1)

```


2. **手焊物理设计图纸**：为了将这个代码打包，你写了一张叫 `Dockerfile` 的只读挂载图纸：
```dockerfile
FROM python:3.10-slim
COPY app.py /app/app.py
WORKDIR /app
CMD ["python", "app.py"]

```


3. **物理刻录**：你运行 `docker build -t yuto-monitor:v1 .`。
* **技术发生**：Docker 引擎把极简 Linux 根文件系统、Python 3.10 运行时环境、以及你的 `app.py` 代码，**压实、编译并分层固化成了一个大约 100MB 的只读二进制文件**。
* **这就是镜像 (Image)**：它现在就是一块冰冻在磁盘上的“死”固件，不费一比特内存，名字叫 `yuto-monitor:v1`。



---

#### 第二步：在内存中强行通电运行 —— 容器 (Container) 的活化

镜像做好了，我们要让这个雷达在服务器上“活过来”抓数：

1. **开闸放水**：你在终端输入 `docker run -d --name live-radar yuto-monitor:v1`。
* **技术发生**：Linux 内核立刻为它开辟了一个绝对隔离的 Namespace。并在那块 100MB 的只读镜像屁股后面，贴上了一个**微型可写层**。
* **唤醒 PID 1**：容器内部编号为 1 的核心物理进程 `python app.py` 瞬间通电，开始疯狂消耗 CPU 时间片。
* **这就是容器 (Container)**：它是活在物理内存（RAM）里的肉身。


2. **查看活体状态**：你敲入 `docker ps`，会看到 `live-radar` 正在 `Up 10 seconds`（运行中）。
3. **捞取物理日志**：你敲入 `docker logs live-radar`，会看到屏幕上啪啪啪不停闪过你代码里打出来的 `⚙️ 正在扫描 Volumes 目录...`。它正活在它独立的小宇宙里。

---

#### 第三步：跨国资产分发对账 —— 仓库 (Registry) 的物流

现在，本地 Mac 测试完美。下个月，要在DTU，将这个雷达部署到学校的常驻高性能服务器上，你总不能用 U 盘把这 100MB 的镜像拷过去。

1. **标记资产标签**：你在 Mac 终端打上你在远程官方仓库（Docker Hub）的个人账号印记：
```bash
docker tag yuto-monitor:v1 yutohuang/datacenter:monitor-v1

```


2. **顺着网线推上云端**：你执行 `docker push yutohuang/datacenter:monitor-v1`。
* **技术发生**：Docker 守护进程把这个镜像的几层只读 Tar 包，按哈希值顺着跨国网络推向 **Docker Hub 【镜像托管仓库 (Registry)】** 的分布式存储中。


3. **海外服务器无缝复活**：登录进实验室的 Linux 服务器，服务器上除了一个 Docker 引擎什么都没有。可以直接敲下：
```bash
docker run -d yutohuang/datacenter:monitor-v1

```


* **终局合拢**：服务器的 Docker 引擎一查本地没数，立刻从 **【仓库】** 里把那几个只读压缩包拉下来（**镜像**），在北欧服务器的内存里瞬间实例化出了一个一模一样的物理隔离进程（**容器**），代码分秒不差地凌空轰鸣运行！

### 通用的Dockerfile模版
```
# 1. 基础镜像层：固定语言+精简镜像
FROM 语言:版本-slim

# 2. 全局工作目录层
WORKDIR /project

# 3. 优先拷贝依赖文件（缓存优化核心）
COPY requirements.txt /project/

# 4. 安装依赖层
RUN pip install --no-cache-dir -r requirements.txt

# 5. 拷贝业务代码层（代码变更不触发重装依赖）
COPY . /project/

# 6. 容器启动入口
CMD ["python", "main.py"]
```
e.g. 
```
# =====================================================================
# Layer 1: 声明基础设施底座。拉取官方微型 Python 固件，比 Ubuntu 镜像小 80%
# 指令：FROM
# 作用：定义镜像的基础父镜像，所有运行环境、系统工具、Python解释器全部来自这个镜像
# 为什么选 python:3.10-slim：
# 1. slim 是精简版Python官方镜像，移除gcc、系统冗余库、文档，镜像体积远小于完整版python:3.10、ubuntu
# 2. 官方镜像安全可信，无第三方污染，漏洞修复及时，生产环境标准选择
# 3. 固定3.10版本，避免环境版本漂移，本地/测试/线上Python版本完全统一
# 价值：大幅缩小镜像大小，加快构建、推送、拉取速度，减少攻击面（容器安全核心）
# =====================================================================
FROM python:3.10-slim

# =====================================================================
# Layer 2: 设置容器内部的工作时空。后续的所有命令和代码都会在这个目录下物理发生
# 指令：WORKDIR
# 作用：1. 创建容器内目录 /app；2. 后续RUN/COPY/CMD默认以/app为当前工作目录，等价自动cd /app
# 为什么不直接用绝对路径：
# 1. 不用每次写全路径 /app/xxx，简化后续所有指令，减少拼写错误
# 2. 统一项目根目录规范，所有代码、依赖、日志集中存放，方便运维排查文件
# 3. 容器运行时默认进入/app目录，启动脚本不用手动切换路径
# 价值：标准化容器内项目目录，降低维护成本，统一工程规范
# =====================================================================
WORKDIR /app

# =====================================================================
# Layer 3: 复制物理资产。将本地电脑当前目录下的文件，拷贝到容器内部的 /app 目录
# 指令：COPY
# 语法：COPY 本地路径1 本地路径2 容器内目标目录
# 作用：把宿主机的代码、依赖清单打入镜像持久层
# 为什么分开拷贝requirements.txt + app.py，不一次性COPY . /app：
# Docker分层缓存机制：每一条FROM/WORKDIR/COPY/RUN都会生成独立镜像层
# 1. 只变更代码app.py时，requirements.txt层不会重建，复用缓存，构建速度极快
# 2. 只有依赖文件修改，才会重新执行pip install，大幅节省构建时间
# 价值：利用Docker缓存机制优化构建速度，是工业级镜像标准写法
# =====================================================================
COPY app.py requirements.txt /app/

# =====================================================================
# Layer 4: 轰鸣安装依赖。--no-cache-dir 是大厂红线，防止 pip 缓存垃圾霸占镜像体积
# 指令：RUN
# 作用：构建镜像阶段执行命令，执行结果永久保存到镜像层
# 参数解释：
# --no-cache-dir：pip安装时不下载缓存包，不存储缓存到镜像，避免镜像膨胀几十MB
# -r requirements.txt：读取依赖清单批量安装第三方库
# 为什么不本地装好再拷贝：
# 本地系统环境和容器隔离，本地pip包无法直接复用，必须在容器内统一安装
# 价值：控制镜像体积，保证依赖环境纯净统一，杜绝本地环境污染容器
# =====================================================================
RUN pip install --no-cache-dir -r requirements.txt

# =====================================================================
# Layer 5: 封印启动命令。镜像死在硬盘里时不执行，只有当你 docker run 活化容器时才会触发
# 指令：CMD
# 作用：容器启动默认执行命令，仅运行阶段生效，构建镜像时不会执行
# 数组格式 ["python", "app.py"] 优势：
# 1. 不会经过shell解析，避免环境变量转义、信号丢失问题（生产推荐exec格式）
# 2. 容器收到kill信号可直接传递给python进程，正常优雅关闭程序
# 区分：RUN=构建镜像时执行；CMD=容器启动时执行
# 价值：定义服务默认启动入口，运维无需手动输入启动命令，标准化上线流程
# =====================================================================
CMD ["python", "app.py"]
```

### 镜像构建
镜像构建命令：
```bash
    docker build -t 镜像名称:镜像版本 . # 镜像名称：可选，默认为当前目录名
```

docker build 的核心作用：根据 Dockerfile + 上下文（build context）逐层生成镜像（Image），全程做分层缓存、文件拷贝、执行命令、配置运行参数。末尾的 . 就是构建上下文目录，docker build 会把这个目录下所有文件打包发给 Docker 守护进程（dockerd）。
** docker build 有个限制 ** ：不能直接读取宿主机任意文件。Docker 的构建进程（dockerd）是独立后台服务，和你的终端隔离。为了安全，它不允许 Dockerfile 随便读取宿主机上别处的文件，只能读取「上下文文件夹」里的内容。

** 执行 build 时流程： **
1. docker 客户端扫描宿主机上下文目录（. 对应的文件夹）；
2. 自动打包目录内所有文件（排除 .dockerignore 匹配的）；
3. 把压缩包传给后台 dockerd；
4. Dockerfile 里的 COPY/ADD 只能从这份打包文件里拿文件。

### 敌动我动看 Logs，翻箱倒柜用 Exec

---

#### 什么时候用 `docker logs -f`？

> **核心时机：【你想知道“此时此刻，这个程序正在干什么，或者它是怎么报暴毙的”】**

你不需要改变容器状态，不需要查看文件，你的核心需求是**流式观测（Observability）**。

* **场景 A：新服务刚通电上线（监控战报）**
你刚把 Olist 数据清洗镜像扔到后台跑（`docker run -d`），你心里没底，不知道它有没有连上数据库。这时候立刻轰入 `docker logs -f`，肉眼盯着它是不是在啪啪啪往下打印 `[Batch 1] 扫描成功`。
* **场景 B：捕获偶发性崩溃（守株待兔）**
你的数据管道跑着跑着，偶尔会因为网络抖动报错。你不能停掉它，于是你挂着 `docker logs -f` 在另一个屏幕上，一边喝咖啡一边盯着。等它报错的瞬间，红字会立刻刷在你的屏幕上，物理抓包成功。
* **场景 C：死后验尸（查明死因）**
任务在凌晨 3 点崩了，容器状态是 `Exited (1)`。这时候它已经没命了，你根本无法进入它的肉身。你必须且只能用 `docker logs`（这时不加 `-f`），强行调出它死前吐出的最后 10 行堆栈报错（比如 `KeyError: 'order_id'`），一秒破案。

---

##### 什么时候用 `docker exec -it`？

> **核心时机：【日志已经无能为力，你需要进入容器的小宇宙里去“翻箱倒柜、人肉刺探”】**

日志往往只告诉你“结果”（比如：`FileNotFoundError`），但它无法告诉你“为什么文件没了”。这时候你需要**侵入式审计（Interactive Audit）**。

* **场景 A：排查路径与配置文件错乱（翻箱倒柜）**
日志大喊一声：`Error: cannot load config.yaml`。你推测是 `Dockerfile` 里的 `COPY` 路径写歪了。这时候 logs 帮不上忙，你必须 `docker exec -it <容器名> /bin/sh` 强行破门而入，在容器里面敲 `ls -la` 甚至 `cat /app/config.yaml`，人肉核对文件到底躺在哪。
* **场景 B：验证容器内部的网络连通性（飞线测试）**
你的 Python 脚本报错说 `Timeout: 无法连接生产环境的 PostgreSQL 数据库`。到底是宿主机防火墙拦了，还是容器内路由丢了？
你 `exec` 钻进容器内部，在容器的绝对隔离网络里直接敲 `ping 192.168.x.x` 或者 `curl -I <数据库网关>`。**在容器里测网络，才是最真实的物理网络对账！**
* **场景 C：核对依赖库版本（账目审计）**
代码报错 `AttributeError: module 'pandas' has no attribute 'X'`。你怀疑镜像里的 pandas 版本被搞错了，你 `exec` 钻进去，直接在容器里敲一记 `pip list` 或者是 `python -c "import pandas; print(pandas.__version__)"`，当场把冒牌依赖抓个正着。

#### 大厂重工业排错标准流演练（两把武器怎么配合？）

在实际的大数据中台运维中，你不是孤立使用它们的，它们是一套组合拳。

1. **第一步（Logs 预警）**：
你看监控发现一个常驻的数据流容器丢数据了，你敲下 `docker logs -f yuto_prod_worker`。
屏幕上疯狂刷出一行字：`Sqlite3.OperationalError: database is locked`。
2. **第二步（Exec 突袭）**：
只看 logs 你不知道是谁锁了数据库。你立刻点击 VS Code 的 `+` 号**开辟第二个并发终端**，一发 `docker exec -it yuto_prod_worker /bin/sh` 犹如特种部队索降、精准攻占容器内部。
3. **第三步（内部人肉审计）**：
你站在容器里的 `#` 提示符后，敲下 `ps -ef`，猛然发现容器里除了你的主程序，居然还有一个卡死的僵尸 Python 进程死死咬着数据库文件不松口！你顺手一记 `kill -9` 把它就地正法，生产系统瞬间恢复通畅。



### 优雅停止容器
向容器内进程发送 SIGTERM 信号，给程序 10 秒时间完成收尾（关闭连接、刷写日志、提交事务、保存数据），超时未停则强制杀死。
```bash
docker stop y你的容器自定义名称
```

### && 逻辑连接符
前一条命令执行成功（容器正常停止），才会执行后面删除命令

### 删除容器
容器停止后仍然占用本地磁盘、占用容器名、占用端口映射，这条命令把整个容器实例彻底清除
```bash
docker rm yuto_prod_worker
```

### 为什么需要释放本地资源
停止的容器不会自动删除，会持续占用磁盘镜像层、存储卷缓存、容器命名空间，堆积多了会占用大量硬盘。
释放容器名称占用，Docker同一台机器不能同时存在同名容器，旧容器不删，新同名称容器无法启动。
标准化更新流程（你 ETL 项目核心场景）

### 什么时候必须执行这条命令
场景 1：版本迭代更新容器（最常用）
你修改了 Dockerfile、更新 ETL 代码、升级依赖，需要部署新版本 worker：
执行这条命令下线旧 worker；

1. docker build 构建新镜像；
2. docker run -d --name yuto_prod_worker ... 启动新版容器。


不执行 rm 的后果：旧容器占着名字，docker run 会直接报错 Conflict. The name is already in use。


场景 2：容器异常卡死、日志堆积、数据错乱

worker 容器跑数据任务出现内存泄漏、报错崩溃、日志打满磁盘：先stop优雅关闭任务进程；rm清理损坏容器，重新拉起干净实例，避免旧容器脏数据残留。


场景 3：切换配置 / 环境变量

修改容器启动参数（数据库连接、DKK 汇率接口、Spark 参数），不能直接改运行中容器，必须删旧容器再重新 run。


场景 4：本地磁盘清理，批量清理废弃容器

长期本地开发会遗留几十只停止的容器，这条命令用来精准清理指定业务容器，释放磁盘空间。
